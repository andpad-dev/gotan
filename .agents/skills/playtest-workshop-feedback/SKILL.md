# ワークショップ・プレイテストとフィードバック作成

## 目的と境界

この skill は、現在のリポジトリの `workshop/` 配下にある Go Conference ワークショップの参加者になったつもりで
問題を解き、参加者体験を改善するためのフィードバックを作る。別リポジトリの教材や一般的な Go 問題のレビューには
そのまま適用しない。

- 入力として、`workshop/<category>/<difficulty>/<topic>/README.md` のパス、難易度、対象範囲、使用ロールが指定されていれば尊重する。
- 明示された対象パス・対象範囲・使用ロールは、下記のデフォルトより優先する。使用ロールが一つだけ明示された場合は
  そのロールだけをプレイし、他の許可ロールは未実施として報告する。対象は指定されているがロールが未指定なら、
  許可されたロールをすべてプレイする。
- 指定がなければ、`workshop/01-packages`、`workshop/02-features`、`workshop/03-cmd-tools`、
  `workshop/04-deep-dive` から、利用可能な初級・中級・上級のシナリオを一つずつ選ぶ。候補パスを `LC_ALL=C sort` で並べ、
  各難易度で `^# `、`^## 設問 `、`^## 調査の入り口` の三つの見出しが存在する最初の README を選ぶ。該当がなければ、
  その難易度で `LC_ALL=C sort` 後の最初の README を選ぶ。構造確認では見出し以外を読まない。
  デフォルトでは各シナリオの許可ロールをすべて試し、選定理由、対象パス、実施したロールを報告する。全シナリオの確認は、
  ユーザーが明示した場合だけ行う。
- デフォルトではシナリオを変更せず、再現可能な改善点を GitHub Issue にまとめる。ユーザーが修正または PR 作成を明示した場合は、
  問題単位の修正と横断的な運営資料の修正を分け、検証済みの Draft PR まで進める。
- GitHub への Issue 作成は、下記の判定を満たす場合だけ行う。良かった点の記録だけでは Issue を作らない。
- ユーザーが read-only、dry-run、Issue を作成しない、または同等の指定をした場合は GitHub を変更しない。
  その場合は Issue 候補、重複確認済み、重複未確認を分けて報告する。
- 実際の参加者への聞き取り結果と、ロールプレイからの推測を混同しない。前者は「観測された参加者フィードバック」、
  後者は「ロールプレイ上の評価」として分ける。同じ観点で両者が食い違う場合、実参加者の観測を優先し、条件の差を記録する。

### 難易度とプレイ可能ロール

シナリオの難易度ディレクトリを正として、次の対応を必ず守る。

| シナリオのディレクトリ | プレイ可能ロール | プレイさせないロール |
| --- | --- | --- |
| `01-beginner`（初級） | 初心者、中級者 | 上級者 |
| `02-intermediate`（中級） | 初心者、中級者、上級者 | なし |
| `03-advanced`（上級） | 中級者、上級者 | 初心者 |

許可されていない組み合わせで難易度適合性を評価しない。ユーザーが禁止された組み合わせを明示した場合は、
プレイ開始前に即時ブロックし、そのロールでのプレイ結果を捏造せず、許可されたロールへの変更が必要だと報告する。

## 前提確認

1. リポジトリ直下の `AGENTS.md`、`workshop/README.md`、対象カテゴリの README を読む。
   シナリオの配置、難易度ごとの設問数、一次情報のたどり方、Go Playground の扱いを把握する。
   ワークショップ全体が対象なら、問題一覧、参加者向けチームガイド、スタッフガイド、班用 Issue template も探して読む。
2. `git remote get-url origin` で対象リポジトリを特定する。GitHub の書き込み対象を推測しない。
3. 可能なら GitHub コネクタを使い、なければ `gh` の存在と `gh auth status` を確認する。
   認証されていない場合はプレイテストとレポートまで進め、Issue を作成できなかったことを明記する。
   ツールのインストールや認証情報の取得を勝手に行わない。
4. `rg --files workshop | rg '/README\.md$'` などで対象候補を確認する。指定されたパスが存在しない、
   `workshop/` 配下でない、難易度がディレクトリと一致しない、または対象を一意に決められない場合は、勝手に置き換えず報告する。
5. 対象シナリオの difficulty directory と上表を照合し、許可されたロールだけを実施対象にする。
6. `AGENTS.md` が指定する Go バージョンと実行環境の `go version` を比較する。異なる場合は出力を未検証事項として記録し、
   バージョン差を理由にシナリオの欠陥と断定しない。
7. README がシナリオディレクトリでのローカルコマンドを案内する場合、`rg --files <シナリオディレクトリ>` で必要な `.go`、
   `go.mod`、テストデータ、プロファイルなどが追跡されているか確認する。コードブロックだけがあり、ファイル名・保存手順がなく、
   clone 後にREADME記載外の準備が必要な場合は、その準備時間と実行不能箇所を参加者体験の欠陥として記録する。
8. Go 1.25以降の `go tool` は事前ビルドされていないbuiltin toolを初回にビルドする。`no such tool` が出た場合は、対象版の
   `$GOROOT/src/cmd/<tool>` を確認し、空のタスク専用 `GOCACHE` で再試行する。初回ビルドの待ち時間はセットアップ時間として残すが、
   既存キャッシュだけが原因ならシナリオの事実誤認と断定しない。

## 全体プレイテストの監査

ユーザーが「全問」「ワークショップ全体」「通して振り返る」と指定した場合、代表問題のサンプリングで完了しない。
`workshop/` 配下の全シナリオと全 `## 設問 N` を列挙し、各設問を `未実施` のまま残さない coverage ledger を作る。
シナリオ単体の採点に加え、次の横断体験を実際のリンクと手順で確認する。

- **初動と環境**: ワークショップ入口だけで、ローカル Go がなくても Go Playground を開き、Run と Share でコード・URLを共有できるか。
  準備に要した時間と詰まりを記録し、ローカル環境構築を暗黙の前提にしない。
- **ナビゲーション**: 入口 → 問題一覧 → category の調べ方 → 各シナリオ、および各シナリオ → 問題一覧・進行ガイド・category の調べ方、
  の往復を全シナリオで確認する。リポジトリのファイルツリーへ戻らないと次へ進めない場合は欠陥として記録する。
- **用語**: `シナリオ` は README 1 枚の問題単位、`設問` は番号付きの問い、`テーマ` は班が調べる対象、といった意味が一貫するか確認する。
  同じ概念に `問題`・`お題`・`テーマ` が混在し、参加者が別物だと読める場合は表記揺れとして扱う。
- **時間と達成感**: 環境準備、問題選択、調査、Issue 記録、統合、発表準備を分けて所要時間を記録する。
  30 分枠の評価では、解答到達だけでなく、一次情報を複数段たどった証拠と班のまとめが残るかを完了条件にする。
- **読解負荷**: 見出しと要点だけを拾う斜め読みでも、問題の目的、回答物、最初の一歩を見失わずに進めるか確認する。
  問題の本質と無関係な設定や説明のために読み戻しが発生しないか、シナリオを通した集中力ポイントが枯渇しないかも記録する。
- **ヒントの運用**: 時間制ワークショップでは「最初から開いてよい」、自習では「まず閉じて試せる」という二つの利用モードが
  参加者向けガイドに明記されているか確認する。ヒントを隠して所要時間だけを水増ししない。
- **並行作業**: 各シナリオで、観測・公式ドキュメント・実装/履歴など少なくとも二つの独立した調査担当へ分けられるか、
  その結果を全員で統合する問いがあるかを確認する。設問番号を配るだけでも、同じページを全員で読むだけでも役割分担成立とは数えない。
- **調査ログ**: 班用 Issue が裸の URL だけで終わらず、「調べた問い」「見た場所と検索語」「分かったこと」「次の一手/不明点」
  「最終的な調査ルート」を各自が残し、最後に一人が統合できる案内になっているか確認する。

探索時間を延ばす改善は、答えを遠ざけることではなく、予想→実測、ドキュメント→ソース、現行仕様→変更理由など、
別担当が集めた証拠を比較・統合する作業を増やす方向で提案する。

## ロールの演技

各ロールは、上表で対象シナリオに許可されている場合だけ使用する。知識量だけでなく、調査の始め方と
チームへの貢献の仕方を変える。実在の参加者を決めつける
ステレオタイプにはせず、以下をプレイテストの観察軸として使う。

### 初心者

- Go の基本は一部知っているが、対象 API、仕様書、Go 本体ソースの読み方に不慣れな日本人エンジニアとして振る舞う。
- 最初は少し遠慮し、「ここまでは分かりましたが、この用語は何でしょう」のように具体的な疑問から話す。
- 入口の見つけやすさ、問題文の理解、ヒントの適切さ、最初の成功体験、詰まったときの復帰可能性を確認する。
- 仲間の説明を受けたら、分かったことを自分の言葉で言い直し、次に調べる問いを出す。

### 中級者

- 実務で Go を使い、標準パッケージやツールの利用経験はあるが、設計背景の調査には慣れていないエンジニアとして振る舞う。
- 問題を小さな調査タスクに分解し、コードを実行して仕様・ドキュメント・実装の対応を確かめる。
- 調査ルートが再現可能か、設問とヒントの難易度が釣り合うか、初心者にも説明可能な中間地点があるかを確認する。
- 初心者の疑問を具体的な実験に変え、上級者の発見を実務上の意味に結び付ける。

### 上級者

- Go の仕様、標準ライブラリの実装、Proposal や Issue の議論まで追えるエンジニアとして振る舞う。
- README の答えを先に信じず、公式ドキュメント、Go 本体ソース、仕様、設計議論の順に検証する。
- 問題が単なる API の説明で終わらず、調査の深掘りと設計判断の理解に到達できるかを確認する。
- 知識で場を独占せず、初心者と中級者が検証できる問いや一次情報のリンクを渡す。

許可されたロールは、少しシャイだが具体的な発見をきっかけに話が広がる日本人エンジニアとして会話する。
冒頭から全員が饒舌だと仮定せず、問題文・実行結果・リンクなどの共有をきっかけに発言が増えるかを観察する。
これは会話の雰囲気を評価するための演出であり、実際の参加者の性格についての主張ではない。

## プレイテスト手順

### 0. 人間の斜め読みと集中力低下を再現する

[読解負荷・文脈・視覚設計の評価基準](references/readability-rubric.md) を読み、初回約 60% 理解の斜め読み、
文脈置換、意味付きリテラル、シナリオ全体と文単位の集中力ポイント、レンダリング後の視線誘導をすべて評価する。
上級問題でも基準を緩めず、難しさは長文や装飾ではなく調査対象に持たせる。
リポジトリ直下から
`go -C .agents/skills/playtest-workshop-feedback/scripts run . ../../../../<README>` を実行し、
最長文、60文字超過文、漢字比率、構造化シグナル比率、MDD推定値、n-gram平均サプライザル、
CRS推定値を記録する。解析器module内では`go run . <markdown>`を使う。
MDDはKagomeの品詞に基づく前方係り受けの推定、サプライザルは対象外のworkshop READMEで学習する
add-alpha単語bigramの値である。neural LMやbase ONNXモデルの値とは呼ばず、`crs_estimate`も
モデル由来のCRSと同一比較しない。

### 1. 先に答えを見ない

候補選定の構造確認では、見出しだけ（`#`、`## 設問`、`## 調査の入り口`）を読む。答えを見ない段階で README 全文を
検索したり URL を一括抽出したりせず、`<details>` 内のヒント・答え・こぼれ話、そこにあるコードと URL を読んだり取得したりしない。
対象 README のタイトル、導入、設問、問題コード、問題文に見えているリンクだけを先に読む。初回調査の上限は 10 分とし、
5 分経過または異なる調査を 2 回試して進展がない時点の早い方で `<details>` 内のヒントを開く。ヒントを読んだ後に
もう 1 回調査し、それでも到達できない場合だけ答えを開く。環境が時間計測に対応しない場合は、この順序と「2 回の調査」を基準にする。答えを読んだ場合は、
読む前にどこまで到達できたかを記録する。

各シナリオについて、次を記録する。

- シナリオの絶対パスまたはリポジトリ相対パスと、想定難易度
- 初見で問題の目的と最初の一歩が分かったか
- 見出し中心の初回読みと約 60% の理解で、観測・調査対象・回答物・最初の行動を言い直してプレイを継続できたか
- `機構必須`・`調査補助`・`置換可能`・`無関係` の文数、置換前後の問題要約、価値テストの結果
- 意味付きリテラルと中立な値の置換結果、元の値から誘発されるが設問では検証しない仮説
- 文脈ノイズとして追加された固有概念と対応関係、誤読・読み戻し・不要な仮説の有無
- 導入後と各設問後の集中力ポイント残量、消費要因、`余裕あり`・`注意`・`継続困難`・`枯渇` の判定
- 各文の集中力ポイント、最低点の文、`目が滑る`・`集中途切れ` の文数
- 最長文、60文字超過文、MDD推定値、漢字比率、STR、n-gram平均サプライザル、CRS推定値。
  methodとqualificationを併記し、モデル由来の値が必要だが未計測なら理由を明記する
- 改行・段落・区切り・強調で注目箇所を拾えたか、図が必要か、図が文章量と読み戻しを減らしたか
- 各設問を一読して「何を調べ、何を回答物として残すか」を日本語として一文で言い直せたか
- 実行結果や panic・コンパイルエラーが問いの前提なら、実際に起こす完全なコードと共有 URL が答えを開く前に見えるか
- README が指示するローカルコマンドを、記載されたファイルと手順だけでその作業ディレクトリから実行できたか
- 詰まった箇所、詰まるまでの操作、ヒントを使った時点
- 設問ごとに、何回目の調査で到達したか（ヒント開封は `H`、答え開封は `A` を付す）と、確定の根拠にした一次情報
- 実行したコマンド、実際の出力、参照した一次情報
- 答えを開いた後に、調査ルートと説明が検証結果に対応していたか

### 2. コードとリンクを実際に確かめる

- README に runnable な Go コードがあれば、変更を加えず scratch directory で `go run` する。
  出力、エラー、実行に必要な Go バージョンを記録する。
- README が `go run .`、`go vet ./...` などを案内する場合は、記載された作業ディレクトリでもそのまま実行する。
  不足ファイルを検証者が暗黙にコードブロックから作って成功扱いにせず、READMEに完全な保存手順がある場合だけその手順を実施する。
- URL は `curl -sS -o /dev/null -w '%{http_code}\n' '<URL>'` などで確認する。リダイレクト、404、認証要求、
  内容が対象と一致しない URL は区別して記録する。
- `pkg.go.dev` の説明だけで技術的な正誤を断定しない。必要に応じてリンク先の Go 本体ソース、仕様、
  Proposal、Issue の周辺文脈までたどる。公開 API の分類は、説明文だけでなく宣言形式を確認して型・変数・関数を区別する。
  一次情報が挙動だけを裏付け、設計背景を裏付けない場合は、背景を「推測」と明記し、答えや Issue で事実として断定しない。
  事実誤認を Issue にする場合は、根拠となる一次情報 URL を添える。
- 実行環境やネットワークの問題で確認できなかった場合、それをシナリオの欠陥と断定しない。
  「未検証のため Issue 化しない」または「環境依存の確認事項」として分ける。

### 3. 許可されたロールをつなぐ

明示されたロールがある場合は、そのロールの結果だけをプレイ結果として扱い、未指定ロールを補って演じない。
明示されたロールがない場合は、そのシナリオで許可された全ロールをプレイする。全シナリオ指定なら、各シナリオを
許可ロールで機械的に繰り返すのではなく、各ロールの主担当プレイと他ロールのレビューを組み合わせる。

チーム共有では、次の順で発言を組み立てる。

1. 初心者が参加していれば、「何が分かり、どこで迷ったか」を共有する。
2. 中級者が参加していれば、迷いを再現可能な実験・検索語・調査手順に変換する。
3. 上級者が参加していれば、一次情報で裏付け、背景や設計上の意味を補足する。
4. そのシナリオで許可された全員で、次回の参加者が一人でも同じ地点まで到達できるかを確認する。

ここで、参加している初心者が質問を出せる、中級者が橋渡しできる、上級者が答えを独占せず根拠を渡せる、という
役割が成立したかを「チームワーク」の根拠にする。該当ロールが不在の場合、その役割を無理に演じて評価しない。
明示されたロールが一つだけの場合、チームワークは `未評価` と記録し、未観察であることを理由に Issue を作らない。
単に参加者が別々に答えを知っているだけなら、協力できたとは評価しない。

## マルチプレイ計測モード

ユーザーがサブエージェントによる複数人実測を明示的に求めた場合、または`add-scenario`のPR前必須ゲートとして呼ばれた場合は、単独ロールの感想で済ませず、
許可されたロールごとに読み取り専用のサブエージェントを起動して同じシナリオを実施する。利用可能なサブエージェント機能が
ない場合、または単に「チームワークを評価して」とだけ依頼された場合は、複数人の独立実測を捏造せず、連携密度と貢献分散度を
ロールプレイ上の評価または `未評価` として報告する。ロールを一人だけ指定された場合も同様に、
協調指標の総合点は算出しない。

四指標を「実測」として扱えるのは、このモードでロールごとに独立したサブエージェントから得たイベントログだけである。
デフォルトモード（一人の実行者または単一のサブエージェントが複数ロールを演じ分ける場合）でも、以降の記録形式で
イベントログを付ければ採点してよい。ただし Interaction と Balance は演じ分けの構成に依存するため、採点表と最終レポートに
「ロールプレイ上の評価（独立実測ではない）」と必ず注記し、この注記付きの点数を単独で Issue の影響根拠にしない。

### 実施手順

1. 難易度表で許可されたロールだけを一つずつ割り当てる。サブエージェントには対象 README のパス、担当ロール、
   「答えを先に読まない」「ファイル・Issue・Git を変更しない」「観察イベントを返す」ことだけを渡し、期待する結論や採点結果は渡さない。
   答え・ヒントの誤露出、別ロールの結論の先渡し、環境エラーで初回順序が壊れた場合は、そのロールの試行を汚染済みとして Discovery の分子・分母から除外し、
   クリーンな再試行ができなければ `未算出` とする。
   `add-scenario`から呼ばれた場合、シナリオ作者と履歴を共有するコンテキストはすべて汚染済みとし、
   最後の内容変更後に起動した新しい独立コンテキストだけを必須ゲートの実測に含める。
2. 各ロールを並行して初回調査させる。設問、実験、一次情報、詰まりを独立に記録させ、`<details>` のヒント・答えを開いた時点を明示させる。
3. 初回調査の結果を、答えを含めない短い「疑問」「観測」「次に検証したいこと」にして別ロールへ順に手渡す。受け取ったロールには、
   その問いを一次情報または実験で検証し、根拠と次の担当を返させる。この共有ラウンドを少なくとも一度行う。
4. 親エージェントは各サブエージェントの返答を時系列の共通イベントログに統合する。同じ事実を複数ロールが報告しても一つの発見として扱い、
   ロール間の受け渡しだけを連携イベントとして数える。サブエージェントの所感を実在参加者の感情や行動とは表現しない。

### 観察イベントの記録形式

各イベントに `id`、`設問`、`turn`、`from`、`to`、`type`、`fact` を付け、次の種別から選ぶ。

| 種別 | 記録する事実 | 集計への使い方 |
| --- | --- | --- |
| `question` | どのロールが何を疑問にしたか | バトンタッチの起点、発言数 |
| `handoff` | 疑問・観測・次の検証を別ロールへ渡したこと | `from`→`to` の方向付きパス |
| `response` | 受け取ったロールが根拠付きの検証結果を返したこと | `handoff` と対になった往復 |
| `experiment` | 実行したコマンド、実際の出力、検証を主導したロール | Discovery と Balance |
| `source` | 参照した一次情報と、確認できた主張 | Discovery の証拠 |
| `stuck` | 進展が止まり、次の一手が定まらなくなった時点 | Recovery の起点 |
| `resume` | 根拠または役割の引き渡しで調査を再開した時点 | Recovery の終点 |
| `hint` / `answer` | ヒントまたは答えを開いた時点 | Discovery の分母・分子 |

`handoff` と、それを受けた別ロールの `response` が同じ疑問に結び付いた組を「往復 1 回」と数える。返答のない一方向の共有は
`handoff_one_way` として別に記録し、往復には含めない。`turn` は共有ラウンド内のロール発言を 1 とし、`resume.turn - stuck.turn` を復帰ターン数とする。
`stuck` がない場合は復帰速度を 5 点、平均ターン数を `N/A (Stuck 0件)` と記録する。これは「詰まらなかった」ことを、速く復帰したことと混同しないためである。

答えを開いた後の照合（答え・こぼれ話との突き合わせ、答え内の URL やコードの検証）で発生した `experiment`・`source` は、
`設問` 欄を `照合` として記録し、四指標の分子・分母のどちらにも含めない。集計対象はプレイ段階（答え開封前）のイベントだけとする。

### Fun & Collaboration Rubric

各シナリオについて、採点前に生のイベント数と設問数を記録する。感情を推測して点数を補わない。4 項目を観測できない場合は総合点を `未算出` とする。

| 指標 | 算出方法 | 1 点 | 2 点 | 3 点 | 4 点 | 5 点 | 必ず記録する数値 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 連携密度 (Interaction) | 役割補完が成立した設問の割合と往復数 | 0%・ほぼ無対話 | 1–33% | 34–66%・偶発的共有 | 67–99% | 100%・全設問で補完 | 往復数、片道数、補完設問数/全設問数 |
| 自発発見率 (Discovery) | `(ヒント前にチームで解決した設問数 / 全設問数) × 100` | 0–20% | 21–39% | 40–60% | 61–79% | 80%以上 | ヒント前解決設問数、全設問数、ヒント・答えを開いた設問 |
| 復帰速度 (Recovery) | `Stuck` から次の検証へ戻る平均会話ターン | 5 ターン以上または断念 | 4.0–4.9 | 3.0–3.9 | 2.1–2.9 | 1–2 ターン（平均 1.0–2.0） | Stuck 件数、各復帰ターン、平均、断念数 |
| 貢献分散度 (Balance) | `(初心者・中級者が主導した experiment 数 / 全 experiment 数) × 100` | 0–20%・上級者独演 | 21–39% | 40–60% | 61–79% | 80%以上、かつ初心者発信の検証を1件以上確認 | ロール別の発言・提案・実験主導数と比率 |

連携密度の「補完」は、質問を出したロールとは別のロールが検証し、質問元または別ロールへ根拠を返した設問とする。
Balance の `experiment` は、単に発言した数ではなく、提案が実行された実験・検証だけを数える。設問数が 0 の場合や、全ロールが同じ答えを
個別に報告しただけの場合は、該当指標を `未評価` とする。

ただし、難易度上許可されたロールに初心者または上級者が含まれない場合は、分子を「許可された中で経験の浅い側のロール」が主導した
`experiment` と読み替える。上級シナリオ（初心者不在）では中級者の主導率を使い、5 点の追加条件も「中級者発信の検証を 1 件以上」とする。
初級シナリオ（上級者不在）では、原式の分子が全 `experiment` と常に一致して指標にならないため、同様に読み替えて初心者の主導率を使い、
5 点の追加条件は「初心者発信の検証を 1 件以上」のままとする。不在ロールを 0 件として扱って不利な点数を作らない。
どの読み替えをしたかは採点表に書く。

総合楽しさスコアは 4 項目の算術平均（5 点満点、小数 1 桁）とする。総合スコアが 2.5 未満、または Recovery が 2 以下なら `要改善` とし、
ヒント設計・設問導線・共有手順のいずれかを原因候補として Issue 化を検討する。これは Issue の自動作成を意味しない。既存 Issue の重複確認、
ユーザーの write 指示、再現手順、具体的な修正案が従来どおり必要である。

Discovery が 100%、Stuck が 0 件に張り付いた場合（AI がロールを演じる実測では起きやすい）、高得点だけを根拠に
「簡単すぎる」「難易度が適切」と断定しない。設問ごとの到達までの調査回数と、確定に使った一次情報のホップ数を採点表に併記し、
難易度の評価はそちらを根拠にする。

採点表は次の形でレポートに添える。

```text
対象: workshop/.../README.md
ロール: 初心者, 中級者, 上級者
設問数: N
Interaction: X/5 (往復 n, 片道 n, 補完 n/N)
Discovery: X/5 (ヒント前 n/N = p%)
Recovery: X/5 (Stuck n, 復帰ターン [..], 平均 p, 断念 n)
Balance: X/5 (初心者 n%, 中級者 n%, 上級者 n%; experiment n)
到達調査回数: 設問1 n / 設問2 n / ...（ヒント開封=H、答え開封=A を付す）
計測方式: 独立実測（マルチプレイ計測モード）・ロールプレイ上の評価（演じ分け）のどちらか
総合: X.X/5 / 判定: 良好・要観察・要改善・未算出
```

## 評価と Issue 作成の判定

各シナリオを従来の「楽しさ・学び・チームワーク」の三軸、読解負荷の三観点、上記の Fun & Collaboration Rubric の四指標で評価する。
六観点には `良好`、`要観察`、`要改善`、`未評価`、四指標には 1–5 点または `未評価` を付け、必ず観察事実を添える。
実行していないロール、実行環境で確認できなかった事項、明示されていないチーム構成は `未評価` とする。

答えや解説の主張は、`観測事実`（実行結果・一次情報が直接示すこと）、`推測`（根拠からの解釈）、
`未検証`（一次情報を確認できないこと）の三つに分類する。`推測` は推測と明記し、`未検証` は事実として採用しない。

- **楽しめたか**: 興味を引く問いがあり、進捗や発見を感じられ、詰まりから戻れたか。
- **学びを得られたか**: Go の挙動だけでなく、一次情報の探し方や設計背景を具体的に説明できるようになったか。
- **チームワークを感じられたか**: 許可されたロールの異なる視点が補完し合い、質問・実験・根拠の共有が成立したか。
- **斜め読み耐性**: 約 60% の理解でも目的、回答物、最初の行動を取り違えず、精読に時間を使わずプレイを継続できたか。
- **文脈集中度**: 機構必須情報と調査補助情報が本質へ収束し、価値のない置換可能な物語や無関係な枝葉へ
  脳内リソースを割かずに済んだか。
- **集中力予算**: シナリオ後半まで集中力ポイントを残し、長文、読み戻し、文脈解読による `継続困難` や `枯渇` が起きなかったか。

Rubric の点数は、主観的な「楽しかった」ではなく、共通イベントログから再計算できることを確認する。点数と根拠となるイベント数が
一致しない場合は、点数を出さず `未評価` とする。マルチプレイ計測モードによらない演じ分けの採点には、採点表の「計測方式」欄で
「ロールプレイ上の評価」と明示する。

次のすべてを満たす「一つの改善課題」ごとに、原則一件の Issue を作る。

1. **根拠がある**: README の該当箇所、再現手順、実行結果、または一次情報との不一致を示せる。
2. **参加者への影響がある**: 楽しさ、学び、チームワーク、斜め読み耐性、文脈集中度、集中力予算の少なくとも一つを明確に損なう。
   `未評価` は影響の根拠にならない。
3. **具体的に直せる**: 問題文、ヒント、答え、コード、リンク、設問順、難易度、共有手順などの修正案がある。
4. **重複していない**: 既存 Issue を検索し、同じ原因・同じ対象の未解決 Issue がない。

次のものは Issue にしない。

- 事実・再現手順・修正案のない好みや印象だけの意見
- ロールプレイだけで、実行環境の制限や未確認の推測に依存する指摘
- 既存の未解決 Issue と同一の指摘。該当 Issue の番号と URL をレポートする
- そのシナリオで許可された全ロールが問題を楽しめ、具体的な学びと役割分担があり、読解負荷の三観点も良好な場合

「全て良かった」場合は、Issue を作らず、評価レポートにその理由と確認範囲だけを書く。小さな気づきを
無理に Issue に変えて Issue 数を増やさない。

## 修正と Draft PR

ユーザーが修正または PR 作成を依頼した場合、Issue 作成だけで終了しない。既存 Issue が同じ問題を扱っていれば参照し、
その Issue を根拠に修正を進める。PR は次の境界で分ける。

- 事実、コード、ヒント、調査ルートの修正はシナリオごとに一件。
- 問題一覧、共通ナビゲーション、Playground の使い方、チーム進行、用語統一など複数シナリオに共通する原因は、関心ごとの横断 PR。
- 全シナリオへの同一リンク追加のような機械変更は一件にまとめてもよいが、難易度ラベルや CI の条件を先に確認する。
- 非機械的な役割分担を全問へ一括で書かない。共通の役割モデルを参加者ガイドへ置き、問題固有の分担だけを問題単位で直す。

各 PR は `origin/main` から作り、リポジトリのテンプレート、日英記載、ラベル、検証規則に従う。全体改善と個別問題の変更を
同じ PR に混ぜない。ユーザーが read-only を指定した場合はこの節を実行しない。

## GitHub Issue の扱い

1. まず実行モードを確定する。ユーザーが Issue 作成を依頼し、対象リポジトリが特定でき、書き込み認証も有効なら `write`。
   read-only、dry-run、Issue を作成しない指定がある場合、または認証が無効な場合は `dry-run` とする。`dry-run` では検索や
   Issue 本文の下書きはできるが、作成・編集・ラベル付与はしない。
2. `write` または `dry-run` で、対象リポジトリと対象シナリオを明示した検索語で既存 Issue を検索する。GitHub コネクタが
   使える場合はそれを優先し、CLI の場合は `gh issue list --state all --search '<検索語>'` などを使う。
   検索結果のタイトルだけで同一性を決めず、該当 Issue の本文を確認する。認証やネットワークのため検索できなかった場合は、
   重複を `未確認` とし、「重複なし」と断定しない。
3. Issue は、別々の原因を混ぜず、同じ原因をロールごとに分割せずにまとめる。複数シナリオに共通する欠陥だけは、
   対象パスを列挙して一件にまとめる。
4. 作成前にタイトルと本文をローカルで組み立てて読み返す。認証情報、個人情報、参加者の実名、不要なログ、
   長いコード断片は含めない。技術的な主張には短い一次情報リンクを付ける。
5. 既存ラベルを確認できる場合だけ、リポジトリで既に使われている適切なラベルを付ける。ラベル名を推測して
   新設しない。
6. `write` で、上記の条件、重複確認済み、タイトル・本文のプレビューを満たす場合だけ作成する。対象リポジトリが不明、
   権限がない、重複が未確認、または同一性が解決できない場合は作成しない。
7. 作成後は Issue 番号、URL、タイトル、対象シナリオ、根拠、作成を見送った指摘を報告する。作成失敗を成功と報告しない。

Issue 本文は、次の構成を基本に日本語で書く。

```markdown
## 概要

<!-- 参加者が何に困るかを一文で書く。 -->

## 対象

- シナリオ: `workshop/.../README.md`
- ロール: 初心者 / 中級者 / 上級者
- 観点: 楽しさ / 学び / チームワーク

## 良かった点

<!-- 問題の価値を保ったまま直すため、確認できた良さを書く。 -->

## 気になった点

<!-- どの操作・条件で、何が起きたかを書く。 -->

## 具体的な修正案

<!-- 作成者が次に取れる変更を、対象箇所とともに書く。 -->

## 再現手順

1. ...

## 期待する状態

...

## 根拠

- 実行結果: ...
- 一次情報: [リンク](https://...)
```

## レポート

最終報告には、次を含める。

- プレイした対象、担当ロール、選定理由、未実施範囲
- 全体指定では、シナリオ数・設問数・実施数が一致する coverage ledger と、入口から戻り導線までの横断監査結果
- 実施したロールの短い所感と、楽しさ・学び・チームワークの根拠。未実施ロールと未評価の軸も明記する
- 斜め読みで保持できた内容、精読なしで継続できたか、文脈ノイズ、読み戻し、集中力ポイントの推移と最終残量
- Fun & Collaboration Rubric の採点表、各項目の生イベント数、総合スコア、`要改善` 判定の有無
- 実行した確認、参照した一次情報、環境による未検証事項
- 作成した Issue の URL と番号、重複として見送った既存 Issue
- Issue 化しなかった軽微な所感と、「すべて良かった」場合の理由
- GitHub の実行モード、書き込みができなかった場合の正確なエラー、重複確認の状態、作成予定だった内容
- 観測された参加者フィードバックとロールプレイ上の評価の区別、作成した Draft PR、Issue のみで残した理由

読解負荷は、少なくとも次の形でシナリオごとにまとめる。

```text
斜め読み耐性: 良好・要観察・要改善・未評価（初回60%理解で保持した内容 / 見落とした重要条件）
文脈集中度: 良好・要観察・要改善・未評価（機構必須 n / 調査補助 n / 置換可能 n / 無関係 n）
文脈置換テスト: 元の要約 ... → 固有名詞を除いた要約 ...（調査・答えが変化したか）
文脈価値テスト: 満たした条件 ... / 追加された固有概念 ... / 対応関係 ...
意味付きリテラル検査: 元の値 [...] → 中立な値 [...]（挙動・問い・答えの変化 / 誘発される不要な仮説）
集中力予算: 良好・要観察・要改善・未評価（100 → 導入 n → 設問1 n → ... → 最終 n）
文別集中力: 最低 n/20（該当文 ...）/ 目が滑る n 文 / 集中途切れ n 文
認知指標: L n / 60文字超 n文 / MDD推定 ... / K ...% / STR ...% / n-gram S̄ ... / CRS推定 ...
視覚設計: 区切り ... / 強調 ... / 図の要否と効果 ...
読み戻し: n 回 / 精読が必要になった箇所: ...
```

評価は「良い／悪い」の印象で終わらせず、次の参加者が同じ問題を実際にプレイしたときに何を体験するかが
分かるように書く。ただし、プレイテストで観察していない事実を補わない。
