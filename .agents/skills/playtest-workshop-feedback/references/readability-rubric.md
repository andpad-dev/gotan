# 読解負荷・文脈・視覚設計の評価基準

## 斜め読みと文脈

最初は見出し、各段落の冒頭、強調、コード、入出力だけを拾う。約60%の理解で観測、調査対象、回答物、最初の操作を
言い直せるか確認し、不足時は斜め読みをもう一周だけ許す。精読や複数回の読み戻しが必要なら斜め読み耐性を下げる。

各文を`機構必須`、`調査補助`、`置換可能`、`無関係`に分類する。固有名詞を第1候補・第2候補・第3候補やA/B/Cへ置換し、
実験、調査ルート、答えが変わらなければ`置換可能`とする。繰り返し使われているだけでは必須とみなさない。

置換可能な文脈は、入力と出力の予想を速める、APIの結果や失敗条件を変える、後続設問で調査・回収する、
一つの短い既知概念に収まる、のいずれかを満たすか確認する。満たさず概念や対応関係だけが増える場合は文脈ノイズである。

値の意味を調べない問題では、業務値、URL、環境名、役職、金額などを`hoge`・`fuga`・`piyo`、
`田中`・`佐藤`・`鈴木`、A/B/Cへ置換する。挙動と答えが変わらなければ元の値を`意味付き装飾`とする。

## 集中力ポイント

シナリオ全体は100ポイントから開始し、設問ごとに戻さない。

| 読解イベント | 消費 |
| --- | ---: |
| 説明文 | 200文字ごとに3（端数切り上げ） |
| 200文字を超える一段落 | 3 |
| 見出しや冒頭から分からない重要条件 | 8 |
| 読み戻し、前の設問への往復 | 8 |
| 価値のない置換可能な固有概念 | 重複を除き1件3 |
| 価値のない置換可能な文、無関係な文 | 1件5 |
| 指示語、未定義語、前提の文脈解読 | 1件5 |
| 異なる役割の段落が空行・リスト・区切りなしで連続 | 1件5 |
| 注目すべき観測・制約・次の操作に視覚的な目印がない | 1件5 |

60以上は`余裕あり`、40–59は`注意`、20–39は`継続困難`、0–19は`枯渇`とする。

各文は別に20ポイントから開始する。シナリオ全体から二重に引かない。

| 1文内の負荷 | 消費 |
| --- | ---: |
| 60文字を超えた文字数 | 1文字0.5 |
| 3個目以降の読点 | 1個1 |
| 括弧やダッシュによる途中の補足 | 1箇所2 |
| 4個目以降の新しい技術・ドメイン概念 | 1個2 |
| 条件・理由・例外・結論を三つ以上詰める | 超過単位1個3 |

12–20は`読みやすい`、8–11は`注意`、4–7は`目が滑る`、0–3は`集中途切れ`とする。
重要な指示文が7以下、または7以下の文が二つ以上なら改善候補とし、最低点の文を引用する。
すべての説明文を60文字以内に収めるよう努める。超える場合は、前提、操作、条件、結論の境界で分割する。

## 認知適合指標

計測対象は、答えを開く前に見える学習者向け文章とする。Markdown記号、URL、コードブロック、折りたたまれた本文、
空白、句読点を比率計算の分母から除く。対象範囲を変えた場合は明記する。

- **MDD推定値**: Kagome IPA辞書の形態素・品詞から文節を近似し、前方の係り先を規則で推定した距離の平均。
  格助詞・係助詞で終わる文節は次の述語、`の`は次の名詞、それ以外は直後の文節へ係るとみなす。
  末尾のroot文節は分母から除く。
  2.5以下を目標にするが、係り受け解析器による正解MDDではない。文ごとの文節、係り先、適用規則をJSONで監査する。
  主語と述語、修飾語と被修飾語を近づけ、修飾語を被修飾語の直前へ置く。
- **漢字比率 K**: 対象文字に占める漢字の割合。30〜40%を許容範囲、35%を目標とし、`ΔK = |K - 35|`を記録する。
  40%を超えたら、過度な熟語を平易なひらがなや日常語へ置き換える。
- **n-gram平均サプライザル S̄**: 対象以外の`workshop/**/README.md`を辞書順に集め、表示文章だけで学習した
  add-alpha単語bigramの`-log2 P(w_i | w_{i-1})`の平均。Kagome IPA辞書で同じトークナイズを行い、
  BOS/EOS、未知語、語彙数、alpha、コーパス件数・トークン数を記録する。正規化された条件付きサプライザルだが、
  neural LMや利用者提供のbase ONNXモデルの値ではない。モデル由来の平均サプライザルと同一視しない。
- **STR**: `T_struct / T_total`。見出し、箇条書き、太字の文字を重複なしで数え、15〜30%を目標にする。
- **CRS**: 次式を使う。`L`は対象内の最長文の文字数とする。

```text
CRS = 100 - (15.0 × max(0, MDD - 2.5)^2
             + 0.5 × max(0, L - 60)
             + 1.0 × |K - 35|
             + 2.0 × S̄)
      + 20.0 × STR
```

付属解析器は、上記のMDD推定値とn-gram平均サプライザルを式へ代入した`crs_estimate`を返す。
これは軽量ヒューリスティックによる推定値であり、係り受け解析器やbase ONNXモデルを使うCRSと同じ尺度だと扱わない。
モデル由来のMDD・サプライザルが必要な評価では、値を捏造せず別計測として明記する。

リポジトリ直下からは次を実行する。

```bash
go -C .agents/skills/playtest-workshop-feedback/scripts run . \
  ../../../../workshop/<category>/<difficulty>/<topic>/README.md
```

解析器module内では`go run . <markdown>`を使う。別のコーパスを使う場合だけ`-corpus <workshop-root>`を指定する。

## 視覚設計

ソース上の折り返しではなく、GitHubでレンダリングされた見え方を評価する。段落は一つの役割に絞り、観測、背景、制約、
操作、回答物が変わる箇所では空行、リスト、表、`---`のいずれかで区切る。意味のない空白や装飾的な区切りは増やさない。

調査で最初に拾うべき観測、比較対象、制約、検索語、次の操作を太字またはインラインコードで目立たせる。
答えや結論そのものは強調しない。一節の大半を強調して差をなくす、色や絵文字だけへ意味を持たせる方法は不合格とする。
見出し・箇条書き・太字の文字量が全体の15〜30%に収まるか確認し、少なすぎる場合は情報の匂いを拾う目印を追加する。
多すぎる場合は強調の優先順位を付け直す。

三つ以上の分岐、状態遷移、階層、順序、対応関係を文章だけで保持させる場合はMermaid図を検討する。
図は調査に必要な関係を一目で示し、対応する説明文や読み戻しを減らす場合だけ採用する。文章をそのまま図へ複製する、
意味付き装飾を増やす、図を読まないと設問が成立しない場合は改善にならない。図なしでも同じ情報へ到達できる短い説明を残す。
