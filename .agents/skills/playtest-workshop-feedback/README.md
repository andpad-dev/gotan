# playtest-workshop-feedback

このリポジトリの `workshop/` 配下にある Go Conference ワークショップを、難易度ごとに許可されたロールでプレイテストし、
参加者体験を評価する skill です。全体指定では全シナリオ・全設問に加え、初動、ナビゲーション、時間配分、用語、チーム作業、
調査ログまで監査します。見出し中心の斜め読みと約 60% の理解でもプレイを継続できるか、無関係な文脈へ注意を奪われないか、
長文で集中力ポイントを使い切らないかも確認します。複数人実測が明示された場合、または`add-scenario`の
PR前ゲートとして呼ばれた場合はサブエージェントを使い、感情を推測せず行動イベントから楽しさ・協調度を数値化します。
根拠と具体的な修正案がある場合、依頼に応じて GitHub Issue または検証済みの Draft PR を作成します。

| 難易度 | プレイするロール |
| --- | --- |
| 初級（`01-beginner`） | 初心者または中級者 |
| 中級（`02-intermediate`） | 初心者・中級者・上級者 |
| 上級（`03-advanced`） | 中級者または上級者 |

## 使用する場面

- ワークショップの問題を参加者目線で試したいとき
- 初心者／中級者／上級者それぞれの詰まりどころを確認したいとき
- プレイテストの指摘を重複のない GitHub Issue にまとめたいとき
- 全問を通して、問題一覧、戻り導線、Go Playground、用語、時間配分、役割分担、班 Issue の記録方法を監査したいとき
- README が案内するローカルコマンドを、clone 後に同梱ファイルと記載手順だけで再現できるか監査したいとき
- Go 1.25以降の `go tool` 初回ビルドと、既存 `GOCACHE` による見かけ上のtool欠落を区別したいとき
- 検証で見つかった問題を、シナリオ単位または横断的な関心単位の Draft PR に分けて直したいとき
- `workshop/<category>/<difficulty>/<topic>/README.md` の難易度適合性を確認したいとき
- 実施ロールを限定したプレイテストの結果を、未評価の観点と分けて報告したいとき
- サブエージェントを使って複数人の調査を再現し、連携密度・自発発見率・復帰速度・貢献分散度を採点したいとき
- 見出しと要点だけを拾う参加者が、精読せずに目的・回答物・最初の行動を判断できるか確認したいとき
- 問題と無関係な設定や枝葉を減らし、長文による集中力低下を防げているか評価したいとき

## 読解負荷評価

初回は見出し、段落の冒頭、強調、コード、入出力を中心に読み、約 60% の理解でもプレイを開始・継続できるか確認します。
表示文は `機構必須`・`調査補助`・`置換可能`・`無関係` に分類します。ドメイン固有名詞を第1候補・第2候補や
A/B/Cへ置き換えても調査と答えが変わらない場合は、問題内で繰り返し使われていても `置換可能` と判定します。
置換可能な文脈が入力と出力の予想を速めず、対象APIの結果を変えず、後続設問でも回収されない場合は文脈ノイズとして記録します。
文字列の意味を調べない問題では、業務を連想させる値も独立して検査します。`#backend-alerts`、URL、環境名などを
`hoge`・`fuga`・`piyo`、`田中`・`佐藤`・`鈴木`、A/B/Cへ置き換えても挙動と答えが変わらなければ、
元の値を `意味付き装飾` として削除・置換候補にします。

集中力はシナリオごとに 100 ポイントから始め、文章量、長い段落、見出しから読めない重要条件、読み戻し、文脈ノイズ、
未定義語の解読で累積消費します。残量 20–39 は `継続困難`、0–19 は `枯渇` として、後半まで問題へ集中できる構成かを評価します。
この値は医学的測定ではなく、シナリオ間の比較と読み疲れの発見に使うヒューリスティックです。

各文にも20ポイントを与え、文字数、読点、途中の補足、新しい概念、条件・理由・例外・結論の詰め込みで減点します。
最低点の文を必ず報告し、重要な指示文が7ポイント以下、または7ポイント以下の文が複数ある場合は改善候補にします。
上級問題でも基準を緩めず、難しさを長い一文ではなく調査対象へ持たせます。

レンダリング後のREADMEについて、段落の役割、空行、リスト、区切り線、強調、インラインコードによる視線誘導も確認します。
調査で注目すべき観測・制約・次の操作が斜め読みで拾えなければ改善候補です。三つ以上の分岐、状態遷移、階層、対応関係を
文章だけで保持させる場合はMermaid図を検討し、図が文章を減らさず重複するだけなら装飾として扱います。

1文60文字以内、MDD推定値2.5以下、漢字比率30〜40%（目標35%）、構造化シグナル比率15〜30%を確認します。
付属のGo moduleは、Kagome IPA辞書で形態素解析し、前方係り受け規則によるMDD推定値を返します。
また、対象外の`workshop/**/README.md`を辞書順に集めたadd-alpha単語bigramから、
正規化したn-gram平均サプライザルを計算します。neural LMやbase ONNXモデルの値ではありません。
これらを使う`crs_estimate`も軽量推定値であり、モデル由来のCRSと同一比較しません。

```bash
# リポジトリ直下
go -C .agents/skills/playtest-workshop-feedback/scripts test ./...
go -C .agents/skills/playtest-workshop-feedback/scripts run . \
  ../../../../workshop/01-packages/01-beginner/cmp-or/README.md

# scripts module内
go test ./...
go run . <markdown>
```

コーパスを明示する場合は`-corpus <workshop-root>`を付けます。

## 定量評価

各シナリオで共通イベントログを作り、次の 4 指標を 1〜5 点で採点します。点数だけでなく、往復数、ヒント前解決数、Stuck 件数と復帰ターン、
ロール別の実験主導数を必ず併記します。

| 指標 | 観測する数値 |
| --- | --- |
| 連携密度 (Interaction) | 疑問の引き渡しと根拠付き応答の往復数 |
| 自発発見率 (Discovery) | `(ヒント前解決設問数 / 全設問数) × 100` |
| 復帰速度 (Recovery) | Stuck 件数、平均復帰ターン、断念数 |
| 貢献分散度 (Balance) | ロール別の発言・提案・実験主導数と比率 |

4 項目の平均が 2.5 未満、または復帰速度が 2 以下なら `要改善` として Issue 化を検討します。Issue 作成には、従来どおり重複確認・write 指示・
再現手順・具体的な修正案が必要です。答えの誤露出や他ロールの結論の先渡しがあった試行は Discovery から除外し、クリーンな再試行ができなければ
`未算出` とします。独立した複数人実測を行わない場合やロールが一人だけの場合は、協調指標を「ロールプレイ上の評価」または `未評価` とします。許可ロールに初心者または上級者がいない場合は、
Balance の分子を、そのシナリオで最も経験の浅い許可ロールが主導した実験として読み替えます（初級では初心者、上級では中級者）。
`add-scenario`のPR前ゲートでは例外なく、作者と履歴を共有しない新しい独立コンテキストで全許可ロールを実測します。

集計対象はプレイ段階（答え開封前）のイベントだけで、答え開封後の照合で行った実験・URL 検証は 4 指標に含めません。
ロールごとの独立サブエージェントによる実測ではなく、一人が複数ロールを演じ分けた採点には「ロールプレイ上の評価」と注記し、
その点数を単独で Issue の根拠にしません。Discovery 100%・Stuck 0 件に張り付いた場合は、設問ごとの到達調査回数を難易度評価の根拠にします。

## 副作用

Issue または修正 PR を依頼された場合に限り、認証済みの GitHub コネクタまたは `gh` CLI で作成します。
read-only／dry-run 指定、認証失敗、Issue の重複未確認の場合は外部変更を行わず、候補・確認済み・未確認を分けて報告します。
すべての評価が良好な場合や、根拠のない印象だけの場合は Issue を作成しません。
