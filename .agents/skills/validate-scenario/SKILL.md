# validate-scenario

ワークショップの README を「答えの正しさ」だけでなく、参加者が同じ調査経路を再現できる教材として監査する。ユーザーが「報告だけ」と指定していない限り、修正が必要な問題ごとに独立した Draft PR を作る。

## 不変条件

- リポジトリ直下の `AGENTS.md` と参照されている指示を先に読む。既存の未コミット変更を混ぜず、対象外の差分を消さない。
- 問題の調査ルートの最初の外部ページは `https://go.dev/...` にする。`pkg.go.dev`、`cs.opensource.google`、GitHub issue から始まる場合は、内容が正しくても導線違反として報告する。
- `go.dev` の入口から、category 直下の README の検索手順、問題文の観測、ヒント、各ページで見つかるリンクだけを順番に使って、答えの根拠へ到達できることを確認する。答え欄にだけ現れる URL や検索語を前提にしない。
- 技術的主張は記憶・検索スニペット・ブログの要約だけで判定しない。必ず Go の一次情報を辿り、必要ならバージョン付きの Go 本体ソースと周辺文脈を読む。
- 「資料から断定できない」「不明」「これは推測である」とすべき箇所は、その不確実性と根拠の限界を答えに明記する。根拠のない推測を事実として通さない。
- ヒントは観測や検索の方向だけを示す。答えの識別子、結論、仕様文の引用、答えを直接開く URL をそのまま置かない。

## 検証ワークフロー

### 1. 対象と前提を確定する

対象を一つの `<category>/<difficulty>/<topic>/README.md` として特定し、次を読む。

1. `AGENTS.md` とリポジトリ内の追加指示。
2. 対象 category の `README.md`。逆引き手順、共通検索操作、入口 URL を記録する。
3. 対象シナリオの全文。設問、ヒント、答え、こぼれ話、調査の入り口、コードブロック、すべてのリンクを対象にする。
4. `.github/pull_request_template.md` と `check-scenarios` workflow。修正 PR の構造と CI の前提を確認する。

問題のパス、難易度、設問数、導入の文脈が `AGENTS.md` の方針に沿っているかを確認する。導入に
固定の定型句がないこと自体はエラーにしない。職場の状況・最初の観測・調べる目的が自然につながり、
難易度に応じた調査体験が読み取れるかを手動で判定する。カテゴリ README が空または導線を提供して
いない場合、問題だけを合格にしない。

### 2. リンクを二段階で調べる

最初に、機械的に判定できる構造と導線の前提を確認する。

```bash
python3 .agents/skills/validate-scenario/scripts/check_scenario_structure.py \
  workshop/<category>/<difficulty>/<topic>/README.md
```

この preflight が `FAIL` を出したら、手動調査で上書きせず不合格として記録する。`WARN` は自動判定できないため、後続の一次ソース・ヒント・Playground の手動検査で解消する。特に `調査ルート` の最初の URL が `go.dev` でない場合は導線不合格であり、答え欄の別のリンクから補ってはいけない。

次に、機械的なリンク候補抽出を行う。

```bash
python3 .agents/skills/validate-scenario/scripts/check_markdown_links.py \
  --network workshop/<category>/<difficulty>/<topic>/README.md \
  workshop/<category>/README.md

python3 .agents/skills/validate-scenario/scripts/check_playground_sources.py \
  --network workshop/<category>/<difficulty>/<topic>/README.md
```

このスクリプトは URL の行番号、相対リンクの存在、ローカルアンカー、HTTP 応答の一次スキャンを行う。終了コード `1` はリンク不合格、`2` はネットワーク障害または判定不能なアンカーを含む `INCONCLUSIVE`、`0` は機械的な失敗なしを表す。`SKIP` は外部 URL を未確認という意味であり、合格ではない。意味が正しいか、ページ内アンカーが狙った見出しを指すかは必ず目視で追加確認する。
`check_playground_sources.py` は共有URLの `.go` ソースを取得し、HTTP応答・ソースのハッシュ・サイズを記録する。これは内容一致の自動判定ではないため、出力されたソースをREADMEのコードと目視で比較する。
ネットワークを指定しない場合やネットワーク障害がある場合は `INCONCLUSIVE`（終了コード `2`）として扱う。

各 URL について、少なくとも次を確認する。

- 相対リンクは対象ファイルから解決でき、リンク先のファイルまたはディレクトリが存在する。
- HTTP URL はリダイレクトを追って `curl -L -sS -o /dev/null -w '%{http_code}\t%{url_effective}\n' '<URL>'` で確認する。`404`、`410`、`5xx`、DNS/TLS 失敗は不合格。`403` や `429` は合格扱いにせず、`要再確認` とする。
- `2xx` でも汎用トップページへのリダイレクト、別の issue、別バージョン、別パッケージなど、本文の説明と違うページなら「誤リンク」とする。
- Markdown リンクだけでなく、裸の `https://...`、Go Playground、コードコメント中の URL、`<details>` 内の URL も確認する。
- `#anchor` はリンク先ページの見出しや識別子に実在し、説明している節を指すことを確認する。動的サイトでは URL の応答だけで済ませず、該当見出しを `find` 相当で探す。
- Go Playground の共有 URL はページが開けるだけでなく、README のコードと同一の内容を表示・実行できることを確認する。実行例だけの共有リンクや別コードへのリンクは誤リンクとする。
- Go Playground は共有ページのHTTPステータスだけで合格にしない。`https://go.dev/play/p/<id>.go` を取得してソースを読み、直前のコードブロック・問題文・記載出力と突き合わせる。`?v=gotip` などの版指定は `.go` URLから落ちるため、README側の版指定も別途確認する。

リンク切れと、到達できるが意図と違うリンクを別の問題として報告する。DNS/TLS/タイムアウトなどネットワーク障害だけで不合格と断定せず、再試行結果を `INCONCLUSIVE` として残す。

### 3. 問題を「答えなし」で歩く

答え欄を根拠にせず、参加者の視点で次の表を埋める。答えの `<details>` を開かない別の scratchpad を用意し、まず `go.dev` の入口を開く。その後は category README、問題文、ヒント、直前のページから得られる検索語・リンクだけを使う。検索エンジンで別の入口を探したり、答え欄の URL を先に開いたりしない。

| 手順 | 今見えている手がかり | 実際に行う検索・操作 | 次に到達した URL/節 | 到達の根拠 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 1 | `go.dev` の入口 | category README の指示に従う | ... | ページ上のリンク/見出し | PASS/FAIL |
| 2 | 前のページで得た用語 | `f`、ページ内検索、リンク追跡など | ... | 直前の情報 | PASS/FAIL |

次のいずれかなら導線不合格とする。

- 最初のページが `go.dev` ではない。
- `go.dev` の入口が問題文、category README、または `調査の入り口` に存在せず、検証者が外部検索で補う必要がある。
- 次の URL、検索語、見出し名が答え欄にしか存在しない。
- 途中の発見から次の検索がなぜ必要か説明されていない。
- 最初の一次情報を飛ばして、設計判断・issue の結論・実装ソースへ直接移動する。
- 「検索する」とだけ書かれ、category README とヒントから検索対象を特定できない。
- 最終回答に書かれた根拠へ、途中のリンクや見出しを辿って到達できない。

入口に最終回答のリンクを並べるだけの構成を許可しない。最終根拠への直リンクは、前段で用語・版・設計上の問いを発見した後の補助リンクとしてのみ認める。

### 4. ファクトを一次ソースで検証する

README から主張を一文ずつ抽出し、次のような証拠台帳を作る。

| 主張 | 種類 | 一次ソース | 確認した箇所 | 実測 | 判定 |
| --- | --- | --- | --- | --- | --- |
| ... | 仕様/挙動/歴史/リンク/推測 | URL | 見出し・ソース行・issue コメント | コマンドと出力 | FACT/INFERENCE/UNKNOWN |

一次ソースの辿り方は主張に合わせて選ぶ。

- 言語仕様はまず `go.dev/ref/spec`。比較可能性、サイズ、構文などの規則を該当節で確認し、必要なら `cs.opensource.google/go/go/+/refs/tags/go1.27.0:...` の実装と周辺コードで挙動を照合する。
- 標準ライブラリは `go.dev` の入口から公式ドキュメントへ進み、`pkg.go.dev` の説明だけで結論を出さず、リンクされた Go 本体ソースのバージョンタグ付きファイルと前後の実装を読む。
- Go 1.26/1.27 の最近の機能は各リリースノートを起点にする。issue 番号が出たら、対応する `github.com/golang/go` の issue 本文・全議論・関連リンクを読み、リリースノートの要約だけで推論しない。
- ツールは `go.dev` または `pkg.go.dev` の公式説明、`go help`、Go 本体の `src/cmd` / `src/cmd/vendor` のソースを照合する。`golang.org/x/...` の挙動を扱う場合も、公式リポジトリのソースまで辿る。
- 歴史・設計判断は、リリースノート → proposal/design → issue の議論 → 採否・実装の順を基本にする。採用された事実、見送られた案、執筆者の推測を分ける。
- `pkg.go.dev` を使ったら、宣言の `cs.opensource.google/go/go` リンクと周辺文脈を必ず読む。Go 本体リンクは `refs/tags/go1.26.5` のように固定する。

コードと出力も主張の証拠として扱う。

- 実行可能なコードは一時ディレクトリで `go run` し、`go version`、実行コマンド、実際の標準出力・標準エラーを記録する。README の出力と一字一句照合する。
- 意図的にコンパイルエラーになる例は `go run` を試し、終了コードと実際のエラーを「コンパイルに失敗する例」として記録する。エラーを成功出力のように書かない。
- ローカルの Go 版が主張の版と違う場合は、版の差を明記し、該当版の Playground・タグ付きソース・適切な toolchain で再確認する。現行版はリポジトリ指示に従う。
- リリースノートが `DRAFT` や「未リリース」と明記されている場合、採用済みの現行仕様として扱わない。リリースノートの状態、`go.dev/ref/spec` の言語バージョン表示、タグ付きGo本体ソースを照合し、将来仕様・gotip・現行版の挙動をREADME内で区別する。
- コンパイルエラーは、READMEに書かれたバージョンと同じツールチェーンで実行して記録する。別バージョンの `-lang` エラーや推測したエラーメッセージを転記しない。
- 実行はREADMEに書かれた作業ディレクトリから、同じコマンドで行う。`go.mod` の有無、`go version`、終了コード、標準出力、標準エラーを記録し、`go ... ./...` がそのディレクトリで実行できない場合は到達可能性のFAILとする。
- 日付・乱数・OSパス・一時ディレクトリなど環境依存の出力は再実行して確認する。固定値を「実際の出力」として残す場合は実行日時・環境を明記し、再現不能な値は期待出力にしない。
- JSON例はレスポンスの型定義と照合する。`[]Candidate` のような型情報がある場合、文字列配列へ簡略化せず、実際のフィールド名・入れ子・型を再現する。
- コードブロックには対応する Go Playground リンクが必要。共有前後にコードが変わっていないことと、`https://go.dev/play/p/<id>` の応答を確認する。

一次ソースが一つの解釈しか支えないのか、複数の解釈を残すのかを確認する。答えが曖昧な場合、README に「不明」「資料からは断定できない」「ここからは推測」と明示し、何が分かっていて何が分からないかを分離する。曖昧さを隠した断定は不合格とする。

主張を次の三つに分類してから判定する。

- `FACT`: 一次ソースまたは再現可能な実測が直接支える事実。
- `INFERENCE`: 複数の事実から導いた解釈。導出過程と「推測」「考察」などの表示が必要。
- `UNKNOWN`: 一次ソースで結論を固定できない、または実行環境・歴史資料が不足している状態。README に不明点と限界を明記する。

`INFERENCE` を `FACT` として書いた場合、内容自体がもっともらしくても不合格にする。逆に、一次ソースが曖昧であることを適切に明示している場合は、未解決であること自体を誤りとしない。

### 5. ヒントの漏洩を検査する

答え欄を折りたたんだ状態で、ヒントだけを読む。各ヒントが「次に何を観測・検索するか」を示しているか、またヒント単独で答えを再現できないかを確認する。

許可するもの:

- category README にある共通操作への誘導。
- 具体的な現象、広い概念、調べる場所、比較する対象。
- プレイヤーが次のページで識別子を発見できる程度の検索方向。

不合格にするもの:

- 問題文にまだ出ていない答えの API 名、型名、キーワード、結論をそのまま書く。
- 答えの仕様文、issue の結論、採否理由を引用または言い換えて書く。
- 答えを直接開く深いアンカーや、答えそのものをタイトルに持つリンクをヒントに置く。
- ヒントを順に読むだけで調査・実験なしに答えを文章として完成できる。

問題文ですでに開示済みの識別子を再度使うこと自体は漏洩ではないが、その識別子の意味や最終結論まで説明したら不合格とする。「まず `f` キーで検索する」のような共通操作は category README に置き、問題ごとのヒントに重複させない。

- 仕様文・Issueコメント・ガイドの結論をヒントにそのまま引用しない。答えに現れる固有の関数名、構造体フィールド、内部関数、エラーメッセージ、採否理由を先に提示していないか確認する。ヒントだけで答えの文章を再構成できる場合は漏洩とする。

### 6. 答えと調査ルートを突き合わせる

答えの **調査ルート** と **答え** を分けて読み、手順を実際に再現する。各設問について以下を確認する。

- ルートの第 1 歩が `go.dev` から始まる。
- 第 1 歩の `go.dev` URL は、問題文・category README・調査の入り口のいずれかから参加者が発見できる。
- 各歩の目的、観測、検索語、次のリンク、見つかる事実がつながっている。
- 前のページから次のページへ、リンクまたは再現可能な検索手順で進める。
- 先に結論・採否・実装を開かず、観測 → 用語/仕様 → 一次ソース → 必要な設計議論 → 実装/実測の順になっている。
- 答えの全主張が証拠台帳にあり、証拠台帳にない主張を答えへ追加していない。
- 最終設問では、冒頭の観測と途中の発見を理由として再解釈している。単に同じ答えを繰り返していない。

「このリンクを開けば分かる」で終わるルート、答え欄にのみ存在する検索語、ページの順序を逆にしている説明は、ファクトが正しくても導線不合格とする。
- `**調査ルート**` は各設問に明示し、設問の入口・観測・検索語・一次ソース・実装/実測の順を保つ。回答欄のURLを直接開かないと成立しないルートは不合格とする。

### 7. 判定と報告を作る

問題ごとに次のいずれかを付ける。

- `PASS`: リンク、導線、一次ソース、実測、ヒント、答えに重大な問題がない。
- `FAIL`: 修正可能なリンク、導線、事実、ヒント、出力、構造の問題がある。
- `INCONCLUSIVE`: 一次ソースやネットワークが確認できず、断定できない。理由と再確認方法を残す。

機械チェックが `INCONCLUSIVE` の問題を `PASS` にしない。外部状態が戻った後に同じ URL・同じコマンドで再確認するまで保留する。

報告は問題単位で、少なくとも次を含める。

```markdown
## <scenario> — FAIL / PASS / INCONCLUSIVE

| 検査 | 判定 | 根拠 | 必要な対応 |
| --- | --- | --- | --- |
| リンク | ... | URL と HTTP/内容 | ... |
| 到達可能性 | ... | 手順 1 → 2 → 3 | ... |
| ファクト | ... | Go ソース/仕様/実測 | ... |
| ヒント | ... | 漏洩の有無 | ... |
| 答えのルート | ... | 直リンク・順序・伏線 | ... |

**修正方針**

- ...
```

`FAIL` には再現手順と最小修正方針を書く。`INCONCLUSIVE` には未確認の主張、試した URL/コマンド、外部状態に依存する理由を書く。複数問題を一つの判定にまとめない。
- リンク検査の `PASS` と、内容が正しいという意味の `PASS` を分ける。HTTP 2xxでも、別のPlaygroundソース、別のIssue、誤ったJSON形、固定された環境依存出力なら `FAIL` とする。

## 修正と問題単位の Draft PR

修正が必要な場合は、対象問題ごとに独立した PR を作る。ユーザーが明示的に報告のみを求めた場合を除き、次の手順を使う。

1. `git status --short --branch` で既存の変更を確認する。対象外の変更を stash、削除、混入しない。必要なら別 worktree を使う。
2. `git fetch origin` の後、`origin/main` から `fix/scenario-<topic>` を作る。既存ブランチを上書きしない。
3. 対象 README と、単一問題の成立に直接必要な変更だけを編集する。共有 category README の不足が複数問題に影響する場合は、category README 用の別 PR に分離し、影響する問題を報告する。
4. リンクの再確認、コードの `go run`、出力照合、一次ソースの再確認、`git diff --check` を行う。
5. `.github/pull_request_template.md` の構造に従い、各セクションを日本語と英語で簡潔に書く。検証で分かった事実、修正内容、確認結果だけを記載し、調査中のメモや未確認の推測を残さない。
6. `gh auth status` で認証を確認する。Conventional Commit の 50 文字以内の短い命令形 `fix: ...` にする。push 後、対象難易度と一致するラベルを 1 つだけ付けた Draft PR を `gh pr create --draft --base main` で作る。認証・権限・ネットワークで作れない場合は、修正済み差分と未完了の PR 手順を報告する。

一つの PR に複数問題の README を混ぜない。修正不要なら PR を作らず、`PASS` と根拠を報告する。一次ソースで解決できない主張を、推測で直すための PR は作らない。必要なら README に不明点と根拠の限界を明記する修正だけを行う。

## 終了条件

検証を終える前に、対象ごとに次を満たす。

- すべてのリンク、コード、出力、アンカーを確認した。
- `go.dev` から始まる調査ルートを、答え欄に頼らず再現した。
- 事実を Go 一次ソースと実測に結び付けた。
- 不明・推測・断定可能な事実を区別した。
- ヒントだけで答えが漏れていない。
- 答えの手順が順序を飛ばさず、冒頭の観測を回収している。
- 修正がある場合は問題単位の差分、再検証結果、Draft PR URL を記録した。
