# add-scenario

問題の作成から Draft PR 作成までを、リポジトリの規約（AGENTS.md）に沿って行う。
問題を「知識を当てるクイズ」ではなく、プレイヤーが観測・検索・仮説検証を重ねて
最後に最初の違和感を説明できる調査体験にする。

## 前提

- リポジトリ直下の AGENTS.md（およびそこから参照される指示）を読み、配置・フォーマット・品質規約を把握する。
- Draft PR を作る場合は gh の認証状態を確認する。認証や権限がない場合は、ファイル作成と検証まで行い、PR 作成を未完了として報告する。

## 設計のゴール

各問題には、次の 5 要素を最初に定義する。

- **簡潔な職場上のきっかけ**: 実務でそのコードや挙動を調べる理由を1文で示す
- **最初の観測**: ログ、コード、出力、挙動など、調べたくなる具体的な手がかり
- **本題**: 最後に説明できる設計・仕様・歴史上の問い
- **検索の連鎖**: ある発見が、次に読む一次情報と次の設問を自然に要求する流れ
- **伏線回収**: 最終回答で、冒頭の観測と途中の少なくとも 1 つの発見（合計 2 つ以上の手がかり）を、なぜそうなるかとして再解釈すること。上級では途中の発見を 2 つ以上回収する。

README を書く前に、次のストーリーマップを scratchpad に作る。

| 設問 | プレイヤーが観測するもの | 今なぜ調べるのか | 次に辿る一次情報 | そこで分かること | 次の手がかり / 最終回収 |
| --- | --- | --- | --- | --- | --- |
| 1 | 具体的な違和感 | 観測を説明するため | ... | ... | ... |
| 2 | 設問 1 の発見 | 発見だけでは説明できないため | ... | ... | ... |

各行には「この発見がなければ次の検索に進む理由がない」と説明できる接続を書く。
設問を独立した FAQ の並びにしない。途中でプレイヤーが立てる仮説と、一次情報で
確認する事実を分け、答えを先に読まなくても小さな発見を積み上げられるようにする。

[読解負荷・文脈・視覚設計の評価基準](../playtest-workshop-feedback/references/readability-rubric.md)を
作成時にも適用する。題材固有の名詞を除いた本題を一文で書く。
調査対象の性質だけを保つ中立な表現へ置き換えても結果が変わらない文脈は削る。
値の意味を調べない場合は、題材固有の意味を持たない中立値を使う。

### 難易度を題材の難しさではなく体験で分ける

| レベル | プレイヤー体験 | 設問の役割 | 避けること |
| --- | --- | --- | --- |
| 初級（01-beginner） | 目の前のコードや出力から用語を見つけ、公式ドキュメントを読めた成功感を得る | 約 2 問。観測 → 用語・基本仕様 → 小さな確認 | Issue の大量読解、歴史的議論を必須にすること、前提知識だけで解ける暗記問題 |
| 中級（02-intermediate） | 実現したい仕事を、候補 API の比較・実験・検証を通じて完成させる | 3 問。失敗の再現 → 実装方針 → 動作確認・トレードオフ | API 名を最初から答えに書くこと、実装手順だけで理由を問わないこと |
| 上級（03-advanced） | 現在の挙動から過去の設計判断・代替案・議論を辿り、最後に背景を説明する | 問数は固定しないが、通常 3〜5 問。観測 → 歴史の入口 → 提案/議論 → 決定 → 伏線回収 | リリースノートの要約だけで結論を出すこと、検索経路のない年表、答えの引用を読ませるだけの問題 |

どのレベルでも、各設問に「観測できる手がかり」「自分で調べる余地」「次へ進む発見」
を置く。上級だけを難しくするのではなく、初級は検索範囲と前提を狭く、中級は実験と
選択を増やし、上級は一次情報の種類と歴史的な不確実性を増やす。

## 手順

### 1. 入力を確認する

次が揃っているか確認する。不足があり、テーマから自明でない場合はユーザーに確認する。

- **難易度**: 初級（01-beginner）/ 中級（02-intermediate）/ 上級（03-advanced）
- **テーマ**: 何を調べさせる問題か（題材のコード・リンクがあれば受け取る）
- **カテゴリ**: 01-packages / 02-features / 03-cmd-tools / 04-deep-dive

テーマの知識量だけで難易度を決めず、上のプレイヤー体験で判定する。指定がなければ
題材の出発点と必要な調査の深さから提案し、勝手に歴史問題へ拡張しない。

### 2. 例題とカテゴリの導線を確認する

該当する難易度の例題 PR（初級 #2 / 中級 #3 / 上級 #4）の diff を gh pr diff で確認する。
マージ済みなら該当ディレクトリの実ファイルを読む。特に本文の分量、設問の粒度、
ヒントの隠し方を合わせる。

`workshop/SCENARIOS.md` のシナリオ一覧と既存シナリオ冒頭のナビゲーションも読み、新しい
シナリオを一覧のどこへ追加し、一覧、`workshop/README.md`、カテゴリ README へどう戻るかを確認する。

カテゴリ README を読み、逆引きの検索手順があるか確認する。カテゴリ README が
なければ作成を提案する。存在しても「まず f キーで検索する」などの共通手順がなければ、
問題のヒントに重複して埋め込まず、カテゴリ README の更新を提案する。

### 3. ストーリーマップと調査ルートを先に作る

ファイルを作成する前に、テーマに対して次を決める。

1. 冒頭の違和感を、実行可能な最小コード・コマンド・ログで再現する。
2. プレイヤーが最初に立てる仮説を 1〜2 個決める。仮説は答えではなく、調査の起点にする。
3. 各設問について「前問の発見 → 新しい疑問 → 検索語/リンク → 発見 → 次の疑問」を書く。
4. 最終設問で、冒頭の観測と途中の発見を引用し直して本題に答える。冒頭の観測と途中の
   少なくとも 1 つの発見（合計 2 つ以上）を、単なる繰り返しでなく理由づけとして回収する。
   上級では途中の発見を 2 つ以上回収し、歴史上の決定と現在の挙動を接続する。
5. 途中で答えが見えてしまうリンクを入口に置かず、一次情報を辿る順序を設計する。
6. 職場設定、登場人物、業務値を、調査対象の性質だけを保つ中立な表現へ置換する。
   調査と答えが変わらない要素はストーリーマップから外す。

上級の歴史問題では、リリースノート → proposal/design → issue の議論 → 採否・実装の
順に辿れることを基本とする。最終決定だけを読む問題にしない。error-stacktrace の
ように、現象から検索を始め、設問をまたいで設計判断に到達し、冒頭の違和感を回収する
構成を参照してよい。ただし、既存問題の答えや固有の事実をコピーせず、題材の一次情報で
裏取りする。

### 4. 一次情報で裏取りする（ファイル作成より先）

- 参照する URL はすべて curl -s -o /dev/null -w "%{http_code}" などで実在を確認する。
- 題材のコードは scratchpad で go run し、実際の出力を取得する。
  - 渡されたコードが動かない場合は、勝手に直さず修正案と理由をユーザーに報告して判断を仰ぐ。
- 問題コード・実行例には Go Playground の共有リンクを作る。
  ~~~bash
  curl -s -X POST --data-binary @main.go https://play.golang.org/share
  # 返ってきた ID を https://go.dev/play/p/<ID> にする。作成後 200 を確認する。
  ~~~
- コードブロックごとに、実測出力と対応する Playground URL を記録する。想定出力や入口 URL
  のみで済ませない。
- 解説の仕様・設計・歴史上の主張は、一次情報（go.dev / pkg.go.dev / Go 本体ソース /
  proposal / issue など）から該当箇所を確認する。
- Go 1.27 を現行版として扱う。最近の機能は Go 1.26 / Go 1.27 のリリースノートから調べる。
  リリースノートに issue 番号があれば、対応する issue の本文・議論・リンク先まで読む。
- pkg.go.dev を使ったら、リンク先の cs.opensource.google/go/go ソースと周辺文脈も読む。
  Go 本体ソースは refs/tags/go1.26.5 のようにバージョンタグ付きでリンクする。

### 5. README を作成する

- workshop/<カテゴリ>/<難易度>/<問題名>/README.md を 1 枚作成する。
- タイトルより前に `[シナリオ一覧](../../../SCENARIOS.md) | [ワークショップ進行ガイド](../../../README.md) | [<カテゴリ> の調べ方](../../README.md)`
  の形式で、一覧、`workshop/README.md`、カテゴリ README への戻り導線を置く。
- `workshop/SCENARIOS.md` の該当カテゴリ・難易度へシナリオのリンクを追加する。新規 README だけを
  作り、参加者が一覧から発見できない状態を完成としない。
- 冒頭は必ず職場の問題として始める。ただし、実務で調査する理由を短い1文で示し、
  すぐに実行・観測できる手がかりへ進む。登場人物、組織階層、業務ルールは、
  対象の制約や答えを変える場合だけ加える。
- 値の意味を調べない問題では、題材固有の意味を持つ値を使わない。
  型、ゼロ値性、順序、等価性など、調査に必要な性質だけを保つ中立値を使う。
- 説明文は1文60文字以内を目標にする。主語と述語、修飾語と被修飾語を近づける。
  修飾語は被修飾語の直前に置き、前提・条件・結論を一文へ詰め込まない。
- 漢字比率は30〜40%（目標35%）、STRは15〜30%を目標にする。過度な熟語を避け、
  見出し、箇条書き、太字で観測・制約・次の操作を斜め読みでも拾えるようにする。
- 三つ以上の分岐、状態遷移、階層、対応関係を覚えさせる場合だけMermaid図を使う。
  文章を図へ複製するだけなら追加しない。
- 初級は用語・基本仕様、中級は実現方法と制約、上級は仕様・設計・歴史的背景を調査する体験に
  する。難易度を定型句で表現する必要はない。
- 設問数は初級 2 つほど、中級 3 つ、上級はストーリーマップを満たす範囲で決める。
- 各設問には、問題、必要なら <details><summary>ヒント</summary>、
  <details><summary>答え</summary> を置く。答えには **調査ルート**（一次情報と順序）と
  **答え**を分けて書き、最後の答えで伏線を回収する。
- ヒントは「次にどの観測・検索をするか」を段階的に示し、用語・結論・リンク先の見出しを
  一度に開示しない。共通の検索操作はカテゴリ README に置く。
- 実行可能な Go のコード・コマンドには、実測出力と個別の Go Playground リンクを付ける。
- 設問、こぼれ話、調査の入り口は --- で区切る。<details> 内に Markdown 見出しを置かず、
  太字ラベルを使う。
- こぼれ話は本題の解決に不要な発見だけにし、必須の伏線や調査ルートを隠さない。
- ## 調査の入り口 には、プレイヤーが最初に開く一次情報をストーリーマップの順序で載せる。

### 6. 答えを閉じて調査導線を監査する

README を書き終えたら、答えの details を閉じた別の scratchpad で、参加者の立場から
各設問を実際に歩く。答え欄の URL、検索語、結論を先に見て補ってはいけない。

#### 6.1 リンクを検査する

- README、`workshop/SCENARIOS.md`、`workshop/README.md`、category README、コードコメント、details 内の Markdown リンク、裸の URL、
  アンカー、Go Playground をすべて抽出する。
- 相対リンクは対象ファイルから解決し、ファイル・ディレクトリ・アンカーの存在を確認する。
- HTTP URL は次でリダイレクト後の URL と status を確認する。
  ~~~bash
  curl -L -sS -o /dev/null -w "%{http_code}\t%{url_effective}\n" "<URL>"
  ~~~
- 2xx でも、汎用トップページ、別のパッケージ、別の issue、別バージョンなど本文の説明と
  違うページへ着地した場合は誤リンクとする。403、429、DNS、TLS、タイムアウトは合格にせず
  INCONCLUSIVE として再確認方法を残す。
- Go Playground はページが開くだけでなく、README のコードと同一のコードを表示・実行する
  ことを確認する。コード変更後に共有 URL を使い回さない。

#### 6.2 go.dev 起点で、答えなしの到達性を検査する

- 各問題の調査ルートの最初の外部ページは必ず go.dev にする。最初から pkg.go.dev、
  cs.opensource.google、GitHub issue、検索エンジンへ飛ばさない。
- category README の共通導線も、最初の外部入口を go.dev にする。既存 category README が
  pkg.go.dev などから始まる場合は、問題のヒントで迂回せず、category README の修正を提案する。
- go.dev の入口から、category README、問題文、ヒント、直前のページで見つかるリンクだけを
  順番に使う。答え欄にしか存在しない URL・検索語・見出しを前提にしない。
- 各設問について、次の表を scratchpad に残す。

| 手順 | 見えている手がかり | 検索・操作 | 次の URL / 節 | 前のページから辿れる根拠 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 1 | go.dev の入口 | category README の手順 | ... | ... | PASS / FAIL |
| 2 | 前のページの発見 | ページ内検索・リンク追跡 | ... | ... | PASS / FAIL |

- 各歩で、なぜ次のページを開くのか説明できるようにする。最初の一次情報を飛ばして
  採否・設計判断・実装ソースへ直行するルートは不合格とする。
- 「検索する」とだけ書かれ、category README とヒントから検索対象を特定できない場合は
  不合格とする。入口に答えの直リンクを並べるだけの構成も不合格とする。

#### 6.3 ファクトを証拠台帳で検証する

README の技術的主張を一文ずつ抽出し、次の分類で証拠台帳を作る。

| 主張 | 分類 | 一次ソース | 確認箇所 | 実測 | 判定 |
| --- | --- | --- | --- | --- | --- |
| ... | FACT / INFERENCE / UNKNOWN | ... | 見出し・ソース行・issue コメント | コマンドと出力 | ... |

- FACT は一次ソースまたは再現可能な実測が直接支える事実だけにする。
- INFERENCE は複数の事実から導いた推測・考察として、導出過程を明示する。
- 一次ソースから断定できない、または環境・歴史資料が不足する主張は UNKNOWN とし、
  README に「不明」「資料からは断定できない」「ここからは推測」のいずれかを明記する。
  分からないことをもっともらしい断定で埋めない。
- 言語仕様は go.dev/ref/spec を起点にし、標準ライブラリとツールは go.dev の公式説明から
  pkg.go.dev やバージョンタグ付き Go 本体ソースへ辿る。pkg.go.dev の説明だけで結論を出さない。
- 歴史・設計判断は、リリースノート → proposal/design → issue の議論 → 採否・実装の順で
  確認し、採用された事実、見送られた案、執筆者の推測を分ける。
- コードの主張は go version、実行コマンド、標準出力・標準エラーを記録し、README の出力と
  一字一句照合する。リポジトリ指定の Go 1.27 と異なる版で実行した場合は版の差を明記する。

#### 6.4 ヒントの答え漏洩を検査する

答え欄を開かず、ヒントだけを上から読む。ヒントは「次に何を観測・検索するか」を示す
導線であり、答えそのものではない。

- 許可: 具体的な現象、広い概念、調べる場所、比較する対象、category README の共通操作。
- 不合格: 問題文にまだ出ていない答えの API 名・型名・キーワード・結論、仕様文の引用、
  issue の結論・採否理由、答えを直接開く深いアンカー、答えそのものをタイトルに持つリンク。
- 問題文で開示済みの識別子を再利用する場合も、その意味や最終結論まで説明してはいけない。
- ヒントを順に読むだけで調査や実験なしに答えの文章を完成できる場合は、ヒントを抽象化する。

#### 6.5 答えの調査ルートを再現する

各設問の **調査ルート** と **答え** を分けて読み、次を確認する。

- 第 1 歩が go.dev から始まり、その URL を問題文・category README・調査の入り口のいずれか
  から参加者が発見できる。
- 各歩に目的、観測、検索語、次のリンク、見つかる事実があり、前のページから次へ辿れる。
- 順序が観測 → 用語/仕様 → 一次ソース → 必要な設計議論 → 実装/実測になっている。
- 答え欄にだけ存在する検索語やリンクに依存していない。
- 最終設問で、冒頭の観測と途中の発見を理由として再解釈し、伏線を回収している。

この監査で FAIL が出たら README を確定せず、リンク・ストーリーマップ・証拠台帳・ヒントへ
戻って修正する。ネットワークや一次資料の取得不能で断定できない場合は INCONCLUSIVE とし、
試した URL・コマンド・再確認方法を記録する。INCONCLUSIVE を PASS にしない。

#### 6.6 読解負荷を計測する

次を実行し、最長文、60文字超過文、漢字比率、STR、MDD推定値、
n-gram平均サプライザル、CRS推定値を確認する。

~~~bash
go -C .agents/skills/playtest-workshop-feedback/scripts run . \
  ../../../../workshop/<カテゴリ>/<難易度>/<問題名>/README.md
~~~

60文字超過文は、前提、操作、条件、結論の境界で分割する。MDD推定値は2.5以下を目標にする。
MDDはKagomeの品詞に基づく前方係り受けの推定であり、正解MDDとは呼ばない。
平均サプライザルは対象外のworkshop READMEで学習したadd-alpha単語bigramの値であり、
neural LMやbase ONNXモデルの値とは呼ばない。`crs_estimate`もモデル由来のCRSと同一比較しない。

### 7. 自己検証する

PR テンプレートのチェックリストに加え、次を 1 項目ずつ確認する。未達なら README を確定せず、
ストーリーマップまたは調査手順に戻る。

**ストーリー検査**

- 冒頭に、実行・観測できる具体的な違和感がある。
- 各設問に「前問の発見が、なぜ次の検索を必要にするか」が書かれている。
- 各設問に、プレイヤーが自分で確かめられる観測または比較がある。
- 最終回答が冒頭の違和感と途中の少なくとも 1 つの発見（合計 2 つ以上）を回収している。上級では途中の発見を 2 つ以上回収している。
- 答えを順に読むだけでなく、プレイ中に仮説を立てる余白がある。

**難易度検査**

- 初級: 公式ドキュメント中心で完走でき、2 問ほどの小さな発見がある。Issue 議論を前提にしない。
- 中級: 3 問が失敗の再現 → 実装の選択 → テスト/トレードオフになっている。候補を比較する余地がある。
- 上級: 設問数に無理がなく、一次資料の種類が段階的に深くなる。採用案と見送り案を区別し、
  最後に歴史と現在の挙動をつなげて説明できる。
- 全レベル: 問題文だけで前提と目的が分かり、ヒントを使っても調査の発見が残る。
- ナビゲーション: `workshop/SCENARIOS.md` の一覧から新規シナリオへ進め、シナリオタイトルより前の
  リンクから一覧、`workshop/README.md`、カテゴリ README のすべてへ戻れる。
- 導線: 最初の外部ページが go.dev で、category README・問題文・ヒントだけで答えの根拠まで辿れる。
- リンク: すべての URL、相対リンク、アンカー、Playground が実在し、本文の説明と一致する。
- ファクト: 技術的主張ごとに Go 一次ソースまたは実測があり、推測・不明が明示されている。
- ヒント: ヒントだけで識別子・結論・答えの文章が漏れていない。
- 答え: 調査ルートの順序を飛ばさず、答え欄にだけある情報を前提にしていない。

**読解負荷検査**

- すべての説明文を60文字以内に収めるよう努め、超過文と分割できない理由を記録した。
- 文脈置換テストで価値のない職場設定・固有名詞・意味付きリテラルを削った。
- 漢字比率30〜40%、STR15〜30%を確認し、範囲外なら読みやすさを保って調整した。
- 観測・制約・次の操作を強調し、段落の役割が変わる箇所を空行やリストで区切った。
- Mermaid図は文章量や読み戻しを減らす場合だけ追加した。

### 8. playtest-workshop-feedback で必ず実プレイする

Draft PRを作る前に、作成したシナリオのパスを指定して
`playtest-workshop-feedback` skillをread-onlyで実行する。作者は答えを知っているため、
作者と履歴を共有しない新しい独立コンテキストを許可ロールごとに起動する。
作者自身のロールプレイは汚染済みとして、必須ゲートの実測に数えない。
各ロールは答えを先に見ず、コード実行、一次情報、斜め読み、文脈置換、集中力、認知指標、視覚設計を確認する。

再現可能な改善点があればREADMEへ反映する。文章、コード、ヒント、答え、リンクを変更した場合は、
変更後のシナリオをもう一度プレイする。最後の内容変更後に完了したプレイテストを最終結果とする。
改善点がなければ変更を無理に作らず、問題がなかった根拠を残す。

次のいずれかに該当する間はPR作成へ進まない。

- プレイテストを一度も実施していない。
- 許可ロールのいずれかが新しい独立コンテキストで完走していない。
- 最後の内容変更後に再プレイしていない。
- `要改善`の指摘、再現不能な手順、技術的な不一致が残っている。
- 軽量MDD・n-gram推定値を、係り受け解析器やneural LMによる値として扱っている。

プレイテストを実行できない場合はシナリオ作成までを報告し、PR作成を未完了とする。

### 9. Draft PR を作成する

~~~bash
git fetch origin
git switch -c feature/scenario-<問題名> origin/main
git add workshop/SCENARIOS.md workshop/<カテゴリ>/<難易度>/<問題名>/README.md
git commit -m "feat: <難易度>問題「<タイトル>」を追加"
git push -u origin feature/scenario-<問題名>
gh pr create --draft --base main --label "<難易度>" --title "<難易度>: <タイトル>"
~~~

- ブランチは origin/main から feature/scenario-<問題名> を作る。
- ラベルは配置ディレクトリと一致させ、初級・中級・上級のうち 1 つだけ付ける。
- PR body は .github/pull_request_template.md の構造・見出し・チェックボックスに従う。
  各セクションは日本語と英語を併記し、未置換のプレースホルダーや案出しの経緯を残さない。
- カテゴリ README の更新を提案した場合は、問題追加と混ぜるか、別変更として明記する。
- Ready 化はユーザーの判断に委ねる。

## 報告

作成した Draft PR の URL、設問のストーリー（各設問の発見と次の検索）、難易度の判定、
裏取りで確認した URL・実行出力、`workshop/SCENARIOS.md` への一覧登録、提案したカテゴリ README の有無を報告する。
最長文、60文字超過文、漢字比率、STR、MDD推定値・n-gram平均サプライザル・
CRS推定値とmethod/qualificationも報告する。
プレイテストの実施ロール、反映した改善、再プレイ回数、最終判定も報告する。
修正点や未完了の検証があれば、影響と次の対応を明記する。
